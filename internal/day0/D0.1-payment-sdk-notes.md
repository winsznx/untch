## 1. Product & protocol identity

- **[VERIFIED · github.com/okx/onchainos-skills · SKILL.md]** The payment layer is officially named **OKX Agent Payments Protocol** (the skill mandates rendering it exactly, bolded). It is a unified dispatcher over three flows:
  1. **x402** — HTTP-402 pay-per-call. Challenge delivered either in the HTTP body (`x402Version` for v1) or via a `PAYMENT-REQUIRED` header (v2). Schemes: **`exact`**, **`aggr_deferred`**, **`upto`** (Permit2-based deferred), **`period`** (subscription via `permit2_subscription`).
  2. **MPP** — `WWW-Authenticate: Payment` challenge; `intent="charge"` (one-shot) or `intent="session"` (multi-request, escrow-contract-backed).
  3. **a2a-pay** — `paymentId`-based, no 402 trigger.
- **[VERIFIED · OKX Learn + The Block + Cryptobriefing]** OKX AI is an agent marketplace where agents register as **Agent Service Providers (ASPs)** and pick **A2A** (escrow, negotiable) or **A2MCP** (instant pay-per-call). Untch's S1 is the A2MCP path.
- **[VERIFIED · OKX x402 doc summary]** OKX's Payment API is "built on the x402 protocol… developer-friendly APIs and SDKs for pay-per-use billing, with payment settlement completed onchain." Settlement modes: **synchronous** (server waits for on-chain confirmation before returning the resource — best for one-off/high-value/low-frequency) and **asynchronous** (resource returned immediately, confirmation in background). Roles: **buyer** and **seller**.
- **Immutable wire identifiers [VERIFIED · SKILL.md]:** headers `X-PAYMENT`, `PAYMENT-SIGNATURE`, `PAYMENT-REQUIRED`, `WWW-Authenticate: Payment`; JSON field `x402Version`; canonical reference `https://x402.org`.

## 3. Auth model

- **[VERIFIED · OKX x402 intro summary]** For raw x402 pay-per-call: "**No registration or OAuth required — pay directly via API using tokens.**" So the buyer flow itself is not gated behind an OKX developer approval.
- **[VERIFIED · repo]** The provisioned credentials are the OKX **REST API HMAC triple** (key/secret/passphrase → `OK-ACCESS-KEY` / `OK-ACCESS-SIGN` / `OK-ACCESS-TIMESTAMP` / `OK-ACCESS-PASSPHRASE`). This is the auth used by OKX's centralized REST + Onchain OS/DEX APIs.
- **[UNVERIFIED — decisive open question]** **Which secret actually settles an x402 payment?** Two candidate models, and the docs would resolve it:
  - **(A) Self-custody:** buyer signs **EIP-3009 `transferWithAuthorization`** with an **EVM private key**, USDT/USDG moves from the buyer's own X Layer wallet. Under this model the API triple is *not sufficient* — we'd need `XLAYER_SETTLEMENT_PRIVATE_KEY` + a funded wallet.
  - **(B) Custodial via OKX account:** the Payment API charges the buyer's **OKX account balance** using the API-key HMAC auth, OKX moves the USDT on X Layer. Under this model the provided triple *plus a funded OKX account* would suffice — no raw private key.
  - The SKILL.md mentions "TEE or local-key sign" for x402, which implies **(A) is at least supported** (local-key signing). Whether **(B)** is also offered is unconfirmed. **This must be resolved before writing the buyer integration line.**

## 4. How a tool is priced (seller / 402 challenge)

- **[VERIFIED · SKILL.md + x402 standard]** Pricing is expressed in the 402 challenge the seller returns. x402 challenge carries (standard field names): `scheme`, `network`, `maxAmountRequired`, `asset` (token contract), `payTo` (recipient), `resource`, `mimeType`, `maxTimeoutSeconds`, plus `x402Version`. Chain is supplied as `methodDetails.chainId` — **`196` = X Layer** [VERIFIED · SKILL.md].

## 10. Divergences from PRD §11 assumptions (top items)

1. **Settlement mechanism is x402/EIP-3009 (likely self-custody signing), not an opaque "Payment SDK charge."** §11 says "every paid call settles via OKX Payment SDK." Reality [VERIFIED]: it's the **x402 protocol** (402 challenge → `X-PAYMENT` → on-chain EIP-3009 transfer → `PAYMENT-RESPONSE` tx hash), dispatched via the **`onchainos payment` CLI / skills**, not a monolithic SDK. Integration must be written against x402 wire semantics. **The buyer very likely needs an on-chain private key + funded X Layer wallet (model A), which §11 does not account for** — this is the single biggest planning gap.

2. **"Our revenue is itself visible marketplace revenue" is only partly grounded.** [VERIFIED] settlement is visible as an **on-chain tx** (`PAYMENT-RESPONSE.transaction` on X Layer) — that's real and explorer-verifiable. But whether it *also* surfaces as marketplace/ASP dashboard revenue is [UNVERIFIED], and being *listed* as an ASP (to accrue "marketplace revenue" with sold-count/reviews per §19) requires **OKX internal review/approval** — a gated step, distinct from raw x402 which is "no registration."

3. **§11's flat "prices in USDT/call" understates the settlement surface.** [VERIFIED] the protocol settles in **USDT *or* USDG** on **X Layer (196)** and supports multiple schemes (`exact`, `aggr_deferred`, `upto`, `period`) and modes (sync/async) — pricing/idempotency (§11 "idempotent by client requestId") must map onto x402 fields (`resource`, `maxAmountRequired`, `asset`, timeout/nonce), not a bespoke request-id scheme. The §11 error envelope `{code,message,retryable,docsUrl}` and "free tier: 20 preflights" are Untch-app conventions that sit *above* x402, not part of it.
