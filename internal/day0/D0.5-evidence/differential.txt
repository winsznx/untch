NUMERIC-POLICY DECISION (recorded in packages/canon/README.md + domain.ts):
  All money amounts and all uint256 values are carried in canonical JSON as decimal STRINGS
  of integer base units — NEVER JSON numbers. JSON numbers are IEEE-754 doubles: they lose
  precision above 2^53 (a uint256 amount cannot survive one) and serialize differently across
  languages. canonUint256() enforces this at runtime by rejecting JS numbers; moneyToBaseUnits()
  converts display amounts to base units using the token's decimals from the verified list.

RFC 8785 EDGES RESOLVED:
  1. Money-as-strings sidesteps the entire RFC 8785 number-formatting surface (es6testfile) for
     every hash we take — canonicalization never depends on float serialization.
  2. Object-key ordering is by UTF-16 code unit, NOT code point. A non-BMP key like the grinning
     emoji (U+1F600, first UTF-16 unit 0xD83D) sorts BEFORE a BMP key at U+F8FF (0xD83D < 0xF8FF),
     opposite to code-point order. Pinned in test/rfc8785.vectors.test.ts.

IMPLEMENTATION NOTE: Surface A wraps the RFC 8785 reference implementation (canonicalize@3.0.0)
and re-runs the RFC's own behaviors against the wrapper (per the D0.5 brief). Surface B uses viem
encodeAbiParameters + keccak256; the Solidity side is keccak256(abi.encode(...)) — NOT encodePacked.
